# ADR 0001 — Cell value storage

**Status:** Accepted
**Date:** 2026-10-03
**Closes:** Q11 (docs/10-open-questions.md)
**Impact:** Data layer, Transform engine, Trace implementation, storage cost

---

## Context

`docs/05-data-model.md` §5.3: the source spec names a `columns` entity but **no entity holds cell
values**. A dataset is 120×8 in the wireframe, but real research datasets span three orders of
magnitude:

| Case | Cells |
|------|------:|
| Wireframe example (§01) | 960 |
| UV-Vis spectrum | ~2,000 |
| HPLC chromatogram | ~50,000 |
| Materials stress-strain | ~500,000 |
| Flow cytometry / NGS matrix | 10⁷ – 10⁹ |

Three shapes were considered.

## Options

### A — Wide table in Postgres

`worksheet_rows(worksheet_id, row_index, values jsonb)`

Simple, transactional, one system. But a 10⁸-cell matrix in `jsonb` means multi-gigabyte TOAST
chunks, poor columnar statistics, and every aggregate is a full JSON scan. Group-by for ANOVA would
be slow at exactly the scale where the platform earns its keep.

### B — Row-per-cell

`column_values(worksheet_id, column_id, row_index, value)`

Normalised, but the row count explodes by the number of columns. 10⁸ cells = 10⁸ rows. Rejected.

### C — Parquet sidecar + Postgres metadata  ✅ **chosen**

Cell values live as a Parquet file in object storage. Postgres holds column *metadata*, *roles*,
*statistics*, and a pointer.

**Parquet** is columnar, typed, compressed, and the native interchange format of the whole
scientific Python stack — `pandas.read_parquet`, `pyarrow`, `scipy`, and `statsmodels` all read it
without a conversion step. Column pruning means an ANOVA over 3 of 40 columns reads 3 of 40.

## Decision

**Option C.** Cell values → Parquet in object storage. Postgres → metadata, roles, statistics, and
a storage pointer.

```
datasets.storage_key        → the uploaded original file (provenance, never mutated)
worksheet.column_store_key   → the derived Parquet file (rebuilt on transformation)
columns.*                    → name, unit, type, roles, error link, stats
```

`worksheet.column_store_key` is regenerated by each transformation; `datasets.storage_key` is
immutable and is what §13 provenance reports as **Source**.

## Consequences

**Gains**
- Postgres stays small regardless of dataset size — only metadata
- Column pruning and predicate pushdown for free
- Trace and Transform are fast: transformations operate on the Parquet frame
- Backups/versioning of data are independent of metadata backups
- Parquet is the lingua franca — exports and future compute engines read it directly

**Costs — accepted deliberately**
- Two storage systems instead of one. More moving parts, more failure modes.
- **No transactional ACID across Postgres and the object store.** Mitigated by treating Parquet as
  an immutable, content-addressed artefact: a transformation writes a new file, then commits one
  Postgres row. A crash leaves an orphaned file (garbage-collected) rather than a dangling pointer.
  The reverse — a committed row with no file — is prevented by writing the file *before* the
  transaction commits.
- Cross-dataset joins cannot use SQL. Accepted: the spec's aggregation is within-worksheet
  (group-by, ANOVA, correlation).

## Implementation rules

1. `datasets.storage_key` is write-once. The uploaded original is never modified.
2. Every `data_transformations` row produces a new `worksheet.column_store_key`.
3. `columns.statistics` (min/max/mean/sd/n_missing/n_distinct) is refreshed after each transform so
   the UI never scans Parquet to populate a column header.
4. A Parquet file is only deleted when no `worksheet` references it.
